# V0.5.3 — 多轮对话质量压测

这一版仍然不增加产品入口，目标是把 V0.5.2 的单轮认知质量基线扩展到 **6～7 轮连续真实对话**。

> 核心问题：用户连续思考 10～20 分钟时，系统能不能稳定地理解“这一轮到底回答了什么”，既不误推进，也不反复追问已经说清楚的内容。

## 压测范围

新增 `evals/multi-turn-dialogue-cases.json`，覆盖全部 8 类认知问题：

- causal：因果解释
- evidence：证据判断
- decision：决策权衡
- problem：问题求解
- concept：概念理解
- perspective：多视角判断
- self：自我反思
- exploratory：探索性思考

共 8 条完整轨迹、53 个用户回答轮次。每一轮都检查：

1. 回答前的认知动作是否正确；
2. 用户本轮是否真的完成了这个动作；
3. `completedMoveEvidence` 是否直接来自本轮原话；
4. 下一动作是否符合 playbook；
5. 下一问是否与最近问题近似重复。

可单独运行：

```bash
npm run stress:dialogue
```

## 压测实际暴露的问题

这轮不是把已有 63 项测试再跑一遍，而是先用连续对话把引擎压出问题，再逐项修复。

### 1. 已回答机制仍会被重复追问

例如：

> 直接拿答案会跳过自己尝试，久了可能减少独立练习。

旧规则没有把这类自然语言识别为 `specify_mechanism`，系统会继续追问“中间哪一步”。现在在当前动作确实是机制说明时，接受更自然的“会……久了会……”“会跳过……减少……”等表达，同时避免把证据句里的“先……再……”误当机制。

### 2. 决策类短回答覆盖不够

例如：

> 暂时不辞。

原规则只覆盖“不参加 / 不去 / 不买”等少数词。现在扩展到辞、留、读、考、换、签、申请等常见决策表达，并支持“目前 / 暂时 / 先”等前缀。

### 3. 具体经历识别过窄

“上周三晚上……”原本不算 `specific_example`，而“最近睡眠太差”反而可能因为出现“最近”被当成具体事件。

现在改为识别“上周 / 周三 / 星期 / 最近一次 / 有一次 / 当时”等更像真实事件的时间锚点，不再把笼统的“最近”自动当成具体经历。

### 4. 不同认知动作之间发生词面串位

压测发现多类典型串位：

- “原始论文或者报告”里的“或者”被误判为 `generate_alternative`；
- “如果看到长期数据，我会重新考虑”被误判为 `test_boundary`；
- “反例是，如果……”同时被当成反例和边界；
- “我必须一开始就写得很好”里的“一……就……”被误判为触发点；
- “写报告 / 做研究 / 收入来源”被“报告 / 研究 / 来源”三个词误判成证据线索。

本版把这些动作的识别条件拆开，减少“出现关键词就完成动作”的情况。

### 5. 局部条件句会覆盖总体判断

用户在边界问题里说：

> 如果 AI 只用来检查自己的思路，我觉得影响可能就不一样。

这只是一个条件/边界，不应立刻把原问题的 `currentPosition` 替换掉。

现在只有以下情况才允许更新总体判断：

- 正在回答 `state_position`；
- 正在回答 `synthesize` 且明确给出判断；
- 在其他动作中显式说“我现在觉得 / 我目前认为 / 我的判断是……”等真正的总体修订。

### 6. “不知道怎么做”在问题求解里被错误当成卡住

在 `isolate_blocker` 中：

> 我卡在第三步，不知道怎么把条件代进公式。

其实已经非常准确地回答了“卡在哪”，不能因为出现“不知道怎么”就判 `stuck`。

现在 `isolate_blocker` 优先识别“我卡在 / 不会的是 / 不明白的是 / 问题出在”等明确卡点表达。

### 7. 边界追问锚定了错误对象

旧的本地模板在 `request_evidence` 后继续做 `test_boundary` 时，会问：

> 你现在的说法是“如果看到长期对照数据……我会重新考虑”。它在什么情况下可能不成立？

这实际上是在给“证据标准”划边界，而不是检查用户对原问题的判断。

本版 `test_boundary` 优先锚定 `currentPosition`。决策题会直接问：

> 你目前的选择是“……”。出现什么情况时，你会改选另一边？

### 8. 撤回理由后，系统还会继续拿旧理由追问

例如用户先说：

> 我觉得会，因为我室友总是直接抄答案。

后面说：

> 前面我举的室友那个例子不能说明整体情况，我撤回这个理由。

旧状态仍保留完整 `currentPosition`，下一问还可能继续围绕“室友抄答案”。

现在：

- 撤回支持理由时，保留结论但去掉 `因为……` 后已经撤回的支撑；
- 撤回整个判断时，清空 `currentPosition` 并重新要求形成当前立场；
- 撤回语句不再被当成新的证据/主张；
- 问题生成提示明确要求不要继续把 `changedIdeas` 中已撤回的理由当成成立前提。

### 9. 混合模式下 AI 可能把旧判断覆盖回来

这是压测中发现的一个更隐蔽问题：

本地规则已经正确识别“撤回理由”并把 `currentPosition` 从：

> 我觉得会，因为我室友总是直接抄答案。

收敛为：

> 我觉得会

但服务端模型如果没有给出新的 `state_position` 证据，会返回调用前的旧 `currentPosition`。客户端原本会无条件优先 AI 字段，于是旧判断又被写回来。

V0.5.3 改为：**只有服务端返回了通过校验的 `state_position` / `synthesize` 完成证据时，AI 才有权覆盖本地 `currentPosition`。** 否则以本地已审计状态为准。

这条已经加入混合模式协议测试。

## 仍然没有被证明的事情

这轮通过只说明：**本地引擎和协议层在这些高风险连续对话上不再出现已知的明显误推进。** 它不证明真实用户一定会觉得追问有价值。

仍需验证：

1. 真实 Provider 在 6～10 轮后是否会语义重复但文字不相似；
2. 模型是否会把用户隐含但未明确表达的观点写进状态；
3. 撤回某条旧依据时，目前只做保守的状态修正，还没有“精确指向哪一条历史证据并标记失效”的完整数据结构；
4. 真实用户是否愿意连续回答，以及哪一问会让用户产生“这个我已经说过了”的感觉；
5. 最终成果是否真的让用户觉得“我想清楚了一点”，而不只是流程完整。

## 下一步建议

V0.5.3 之后，不建议马上继续增加单人功能。

先用真实 Provider 受控跑 5～10 条完整会话，并人工给每一问打分：

- 上下文贴切；
- 动作一致；
- 追问增量；
- 是否重复；
- 是否过度替用户推断；
- 用户是否愿意继续回答。

这一步稳定后，再进入 V0.6 Community MVP，让用户公开“自己确认后的思考成果”，并验证别人是否愿意点「从这里开始我的思考」。
