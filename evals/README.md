# V0.5 认知体验评估

`cognitive-cases.json` 是八类问题的本地回归样例，由 `npm test` 检查分类、首次动作与回答后的下一动作。它只证明这些样例的流程符合预期，不能证明用户思考质量提高。

真实模型与用户试用需要另行评估。建议每条问题按 0（不满足）、1（部分满足）、2（满足）记录：

- 上下文贴切：引用的表达确实来自用户，没有虚构经历或立场。
- 动作一致：这一问推进引擎指定的动作，没有代替用户下结论。
- 负担适当：一次一个任务，用户知道从哪里回答，卡住时能降低难度。
- 反馈准确：描述实际表达，允许用户纠正，不将结论不变当作失败。
- 收获可确认：用户能指出一个发现、依据或尚待验证的问题；系统不代为宣称进步。
- 回访有理由：后续观察与用户自己保存的计划有关，支持不确定、失败及相反结果。

另记录完成时间、使用提示的位置、主动暂停原因和用户下一次有真实问题时是否回来。聊天轮数和停留时间不能单独作为成功标准。

优先补充：不知道、短回答、跑题、矛盾、观点没有变化、提出条件后又撤回、问题里包含多个问号、没有实际证据、验证结果不支持原判断。

## 2026-10-04 补充边界回归

`cognitive-edge-cases.json` 专门覆盖容易被关键词抢占的问题分类，例如第一人称行为模式中出现“选择”，以及“选择”作为概念词而不是决策动作的情况。

`tests/engine.test.mjs` 还逐一覆盖 20 种认知动作的“我不知道 + 动作关键词”反例，防止“提到了前提/证据/例外/边界”等词就被误判为完成动作。

## V0.5.2 对话质量基线

`dialogue-quality-cases.json` 覆盖部分回答、重复回答、观点修订、撤回依据、短但有效回答、拒绝当前方向、显式跑题和一轮多动作等高风险情况。

自动化回归只验证“系统没有明显误推进”。真实体验仍应人工记录追问增量：如果删除某一问不会让用户少想清楚任何东西，该问应标记为低增量并进入后续评估。
